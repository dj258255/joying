# 안읽음을 커서 하나로 줄여도 방 30개 목록이 견뎠다

[두 방법 측정](unread-two-ways.md)이 "캐시의 값이 작다"고 판정한 뒤의 후속이다.
카운터 캐시를 버리고 커서(lastReadSequence 초과 집계) 하나로 가는 것의 남은
질문은 방이 많은 사용자였다. 방 목록 한 번에 집계가 방 수만큼 돌기 때문이다.
가설과 판정 기준은 [#116](https://github.com/dj258255/joying/issues/116)에 먼저
적었다.

결론부터.

- **커서 단일을 채택했다.** 방 30개(바쁜 방 1개 5만 건 + 보통 방 29개) 목록의
  p95 가 36.8ms 로 사전 기준(100ms)의 1/3이다. 안읽음의 자리가 정본 하나가
  되어 멱등 재전송 이중 증가(#99)와 축출로 어긋나는 unread 캐시(#100의 절반)가
  구조로 사라진다
- **멱등 재전송의 이중 증가(#99)를 막았다.** 같은 전송 식별자로 두 번 보내면
  수선 전 코드는 카운터를 두 번 올린다(같은 테스트가 실패하는 것으로 재현).
  멱등 히트와 동시 진입의 제약 패자 모두 올리지 않게 바꿨다
- **"비동기로 옮기면 끝"이 아니었다.** 송신 경로의 배지 갱신을 비동기로만
  옮기자 몰린 송신 40건이 집계 40개로 변해 커넥션 풀에서 저장과 다퉜다(전달
  p95 1,607~2,666ms). 배지는 상태라 마지막 값만 의미가 있으므로 방 · 수신자별로
  대기 중 집계를 하나로 접었고(coalescing), 그 뒤 커서 모드의 전달 p95 가
  카운터와 동급(459 대 485ms)이 됐다

## 잰 조건

| 항목 | 값 |
|---|---|
| 서버 | 1대(8080), 모드는 `joying.chat.unread.mode=counter\|cursor` 로 교체 기동 |
| 시드 | 방 30개(9501~9530), 바쁜 방 9501 에 50,000건, 나머지 200건씩, 읽은 지점 10 고정 |
| 목록 조회 | GET `/api/v1/chat-rooms` 30회씩, 첫 호출은 워밍으로 버림 |
| 쓰기 증폭 | 실제 경로(STOMP) 40건, 키 값의 전후 차이 |
| 전달 왕복 | k6 order-modes, 바쁜 방에서 쌍이 20건씩 교환, 모드마다 2회 |
| 시작 load | 목록 4.6(counter) · 3.9(cursor), 전달 왕복 7.9~16.0 (실행별 기록) |

실행: `load/run-unread-cursor-single.sh counter|cursor`
(원자료 `load/results/unread-cursor-single-*.csv`)

## 결과

방 목록 조회 (각 30회):

| 경로 | 중앙값 | p95 |
|---|---|---|
| counter 히트 | 8.7ms | 17.7ms |
| counter 미스(30방 집계 + 캐시 적재) | 31.9ms | 49.4ms |
| cursor (항상 30방 집계) | 22.4ms | 36.8ms |

쓰기 증폭 (메시지 40건): counter 는 번호 +40 · 안읽음 +40(건당 Redis 2회),
cursor 는 번호 +40 · 안읽음 0(건당 1회).

송신 경로의 전달 왕복 (바쁜 방, 실행 2회씩):

| 구성 | p95 |
|---|---|
| counter, 배지 갱신 동기(수선 전 구조) | 482ms |
| cursor, 배지 갱신 동기 | 631ms (1.31배) |
| cursor, 배지 갱신 비동기(접지 않음) | 1,607 · 2,666ms |
| cursor, 비동기 + 집계 접기(채택) | 485 · 274ms |
| counter, 같은 최종 코드 | 459 · 262ms |

전 실행 유실 0 · 뒤집힘 0 (k6 요약 messages_missing · order_inversions).

## 판정 (잰 뒤에 기준을 바꾸지 않았다)

| 가설 · 기준(#116 원문) | 결과 |
|---|---|
| H6: 커서 단일의 방 30개 목록 p95 100ms 이하면 채택 | **지지** (36.8ms) → 커서 단일 채택, 기본값 cursor |
| H7: 현행은 멱등 재전송에 2, 수선 후 1 | **지지.** 수선 전 코드에서 같은 테스트가 "2회 증가"와 "제약 패자도 증가"로 실패, 수선 후 통과 |
| 쓰기 증폭 2회 → 1회 | 확인 (위 표) |
| 전 측정 유실 0 | 충족 |

## 왜 그런가

- **집계 30개가 37ms 인 이유**: 집계는 `(chat_room_id, sequence)` 인덱스 범위
  카운트고, 방마다 서로 독립이라 chatQueryExecutor 로 병렬로 난다. 30방 중
  바쁜 방 하나만 비싸고 나머지 29개는 수 ms 대다
- **비동기가 역효과였던 이유**: 송신은 40건이 몰리는데 배지 집계도 40개가
  쌓인다. 커넥션 풀은 유한하므로 집계가 저장(동기, 보낸 사람이 기다림)의
  커넥션을 뺏는다. 늦어도 되는 일이 늦어지는 건 괜찮지만, 늦어도 되는 일이
  급한 일의 자원을 뺏는 건 다른 문제다
- **접기가 안전한 이유**: 배지는 누적 상태고 이벤트는 마지막 값만 의미가 있다.
  실행에 들어가며 대기 표시를 비우므로, 집계 중에 온 메시지는 다음 갱신을
  다시 잡는다. 마지막 값은 결국 나간다

## 대가

- 배지 이벤트의 lastMessage 본문은 몰린 송신 안에서 한 박자 늦을 수 있다
  (접힌 갱신은 접은 시점의 메시지 본문을 실음). 목록을 열면 맞는 값으로 읽힌다
- counter 모드는 코드에 남아 있다(설정 한 줄로 복귀). 수십만 건 방이 흔해져
  집계가 기준을 넘으면 그때 캐시를 다시 검토하되, 그 캐시는 무효화 경로부터
  설계한다

## 아직 하지 않은 것

- **수십만 건 방.** 바쁜 방 5만 건 기준이다. 집계가 어디까지 선형인지 재지 않았다
- **방 수백 개 사용자.** 30개 기준이다. 병렬 폭이 chatQueryExecutor 풀 크기에
  막히는 지점을 재지 않았다
- **#100 의 나머지 절반.** unread 캐시 키는 사라졌지만 번호 키
  `chat:sequence:{roomId}` 의 축출 위험은 그대로 남아 있다
