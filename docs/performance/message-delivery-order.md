# 부하를 넣으니 받는 순서가 번호 순서와 달랐다

## 왜 다시 쟀나

메시지에 방 단위 번호를 붙이고 단위 테스트로 확인했을 때 뒤집힘은 0이었다.

그때 잰 것은 **저장된 번호의 순서**다. 저장소에 직접 넣고 정렬해서 셌다. 사람이 쓰는 경로는
그것과 다르다. 웹소켓으로 보내고, 서버가 번호를 붙여 저장하고, Redis로 발행하고, 다시
웹소켓으로 내보낸다. 그 사이에 스레드 풀이 여럿 있다.

**받는 쪽에 닿는 순서**를 재려면 실제 경로로 부하를 넣어야 한다.

## 잰 조건

| 항목 | 값 |
|---|---|
| 도구 | k6 (STOMP 프레임 직접 생성, SockJS 우회) |
| 서버 | 로컬 단일 노드, Spring Boot 3.5.6 / Java 17 |
| 저장소 | MySQL 8.0 · MongoDB 7.0 · Redis 7 (전부 컨테이너) |
| 부하 | 관찰자 1명이 붙은 방에 발신자 8명이 각 25건, 총 200건을 연결 직후 몰아서 전송 |
| 세는 것 | 관찰자가 받은 순서에서 번호가 앞엣것보다 작아진 횟수 |
| 실행 | 설정마다 3회. 예열 실행은 버리지 않고 그대로 적는다 |

실행: `k6 run load/k6/message-order.js`

## 결과

| | 뒤집힘 (200건 중) | 왕복 중앙값 | 왕복 p95 |
|---|---|---|---|
| **고치기 전** | 67 · 73 · 71 | 849ms · 445ms · 371ms | 1.36s · 802ms · 717ms |
| **고친 뒤** | 0 · 0 · 0 | 1.45s · 1.24s · 1.29s | 2.45s · 2.25s · 2.39s |

사라진 메시지는 양쪽 모두 0건이다.

**순서를 얻는 대신 지연을 줬다.** 왕복 중앙값이 약 3배, p95가 약 3배 늘었다. 이것이 이
선택의 값이다.

## 어디서 뒤집혔나

세 군데였다. 하나씩 막고 다시 재면서 찾았다.

### 1. 들어오는 채널

Spring의 `clientInboundChannel`은 스레드 풀이다. 한 연결에서 연달아 보낸 프레임이
서로 다른 스레드로 가서 앞지른다. 나중에 보낸 것이 먼저 번호를 받는다.

계측해 보니 같은 발신자의 연속 메시지끼리도 번호가 어긋나 있었다. `vu3` 이 세 번째로
보낸 것이 40번, 네 번째가 38번, 여섯 번째가 33번이었다.

연결 식별자로 스레드를 골라 한 줄로 세웠다. Spring이 넘겨주는 것은 연결을 모르는
`Runnable` 이지만 그 안에 처리할 메시지가 들어 있고, 헤더에 연결 식별자가 있다.

### 2. 메시지 처리 풀

저장과 발행을 조회용 풀에 던지고 있었다. 같은 방의 메시지가 네 스레드에 흩어졌다.
번호는 원자적으로 발급되므로 정확한데, 저장과 발행이 끝나는 순서를 풀이 정했다.

방 번호로 스레드를 골라 그 방의 일을 한 줄로 세웠다. 방 안에서는 순서대로, 방끼리는
그대로 동시에 돈다.

### 3. 나가는 채널

`clientOutboundChannel` 도 스레드 풀이라 한 사람에게 갈 두 건이 서로 앞지른다.
`setPreservePublishOrder(true)` 로 켰다.

## 왜 세 개를 다 막았나

하나만 막으면 수치가 안 움직인다. 실제로 2번만 막고 쟀을 때 193이 나왔고, 처음에는
고친 것이 소용없다고 판단할 뻔했다.

| 막은 곳 | 뒤집힘 |
|---|---|
| 아무것도 안 막음 | 67 ~ 73 |
| 메시지 처리 풀만 | 여전히 뒤집힘 |
| 셋 다 | 0 |

## 재는 자리를 두 번 틀렸다

이 실험에서 두 번 잘못 쟀다. 둘 다 수치가 그럴듯해서 한동안 눈치채지 못했다.

**첫 번째.** 앱이 안 뜬 상태에서 재고 0을 얻었다. 빌드가 실패했는데 k6는 연결 실패를
조용히 넘겼다. 0은 결함이 없다는 뜻이 아니라 아무것도 재지 않았다는 뜻이었다. 그 뒤로는
잴 때마다 8080 포트에 무엇이 떠 있는지 먼저 확인한다.

**두 번째.** 전송 식별자를 실행마다 같은 값으로 만들었다. 두 번째 실행부터는 멱등이
걸려 서버가 예전에 저장한 것을 그대로 돌려줬다. 200건 중 153건이 예전 번호였고, 그것을
새 번호와 섞어서 세고 있었다. 고쳐도 193이 그대로였던 이유다.

멱등이 제대로 도는 것이 실험을 망친 경우다. 실행마다 다른 꼬리표를 붙여 해결했다.

## 잰 김에 본 것

Redis 구독 컨테이너가 실행기 지정 없이 돌고 있었다. 기본값은 메시지마다 새 스레드를
띄우는 방식이라, 200건을 보내면 `redisMessageListenerContainer-1` 부터 `-399` 까지
**메시지 하나당 스레드 하나**가 생긴다. 로그에서 200개의 서로 다른 스레드 이름을 확인했다.

이번 변경으로 순서 문제는 앞단에서 해결됐지만 스레드가 계속 생기는 것은 그대로다.
따로 다룬다.

## 아직 하지 않은 것

- **두 노드에서 재지 않았다.** 단일 노드에서만 쟀다. 서버가 둘이면 Redis를 건너는
  구간이 하나 더 늘어난다.
- **지연을 줄이려 하지 않았다.** 순서를 얻은 대가로 늘어난 지연을 그대로 뒀다.
  줄이려면 방 단위 줄을 더 잘게 쪼개야 하는데, 그러면 순서가 다시 흔들린다.
- **Redis 구독 컨테이너의 스레드 폭증을 고치지 않았다.** 순서와 별개 문제라 나눴다.
- **장애 주입은 하지 않았다.** 번호를 받은 뒤 저장이 실패하거나 늦어질 때 어떻게 되는지는
  아직 재지 않았다.
