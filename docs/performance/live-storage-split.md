# 대화가 진행되는 동안 메시지 저장소를 통째로 옮겼다

살아 있는 채팅의 메시지 테이블(310만 행)을 메인 DB 에서 전용 DB 로 쓰기 중단
없이 분리했다. 이중 쓰기 → 스로틀 백필 → 검증 → 배리어 컷오버 순서다. 가설과
판정 기준은 재기 전에 [#105](https://github.com/dj258255/joying/issues/105)에
박아 두었다.

결론부터.

- 310만 행을 333초에 옮기는 동안 전달 유실 0, 순서 뒤집힘 0이었다. 컷오버의
  쓰기 배리어는 445ms, 옮긴 뒤 행 수와 체크섬이 전부 일치했다
- **백필 속도가 균형점을 가른다.** 초당 1만 행까지는 전달 p95 가 평시의 1.5배
  안에 머물렀고, 상한을 풀자(실효 약 2만 행/초) p95 가 7.4~19.5초로 폭발했다.
  이 지형의 균형점은 초당 1만 행이다
- 흥미로운 것은 극한에서도 깨진 것이 지연뿐이라는 점이다. 무제한 백필이
  전달을 19초까지 밀어도 유실과 뒤집힘은 0이었다. 밀리는 것과 깨지는 것은
  다른 축이다

공개된 플레이북(이중 쓰기 → 백필 → 검증 → 컷오버. Discord 가 수조 건을 이렇게
옮겼고 Slack 은 라이브 트래픽 중에 샤드를 쪼갰다)을 따르되, 그 글들이 수치로
보여 주지 않는 것을 쟀다. **이관이 진행되는 동안 실시간 전달이 얼마나
밀리는가**다.

## 왜 했나

[postgresql.md](../migration/postgresql.md)의 "아직 하지 않은 것" 첫 줄이
데이터 이관이었다. 코드만 옮겼고 살아 있는 데이터를 옮기는 일은 미뤄 뒀다.
메시지는 가장 빨리 자라는 테이블이라 메인 DB 와 운명을 같이 두면 다른 도메인의
부하와 VACUUM 을 나눠 맞는다. 언젠가 분리해야 한다면 무중단으로 하는 법을
미리 갖추고, 그 비용을 숫자로 알아야 한다.

## 역할을 나눈 이유

| 조각 | 자리 | 이유 |
|---|---|---|
| 이중 쓰기(동기 upsert) | 앱 (ChatStorageMigration) | 새 메시지의 정합은 송신 경로의 일이다. 비동기는 실패가 조용해지고 조용한 실패는 거짓 성공의 모양이라 동기를 골랐다. 실패해도 송신은 막지 않되 지표로 센다 |
| 백필 | 앱 밖 (scripts/backfill-chat-messages.sh) | 옮기는 속도는 라이브 전달과 자원을 다투므로 앱의 생명주기와 분리해 따로 조절해야 한다. 커서 기반이라 중단한 자리에서 다시 시작한다 |
| 검증 | 앱 밖 (scripts/verify-chat-split.sh) | 행 수 + 꼬리 1,000행 체크섬 + 결정적 해시 표본 체크섬. 무작위 표본은 양쪽이 다른 행을 뽑아 비교가 안 되므로 md5(id) 접두사로 뽑는다 |
| 배리어 컷오버 | 앱 + 스크립트 (cutover-chat-split.sh) | 배리어 동안 새 저장이 없으므로 꼬리를 긁으면 잔여가 0이 된다. 배리어는 노드마다 따로 서므로 모든 노드에 올린다. 상한 5초를 넘기면 송신을 살리고 컷오버를 실패로 처리한다 |

백필과 이중 쓰기는 같은 행을 서로 다른 순서로 넣을 수 있다. 둘 다
`ON CONFLICT (id) DO NOTHING` 이라 어느 쪽이 먼저든 최종 상태가 같다(멱등).

## 잰 조건

| 항목 | 값 |
|---|---|
| 서버 | 두 프로세스(8080 · 8081), 순서 모드는 현행(node), 배치는 같은 노드(스티키) |
| 옛 DB | 메인 PostgreSQL 16 (5432). 이관 대상 310만 행(시드 300만 + 기존 실험 데이터) |
| 새 DB | 전용 PostgreSQL 16 (15432, compose profile `chat-split`) |
| 전달 측정 | [#91](https://github.com/dj258255/joying/issues/91) 하네스 그대로. 쌍 1 × 각 100건, 실행별 시작 load 를 CSV 에 기록 |
| 백필 실효 상한 | 측정 전에 무제한으로 15초 돌려 캘리브레이션: 약 2만 행/초. 3단은 5천 · 1만 · 무제한으로 정했다 |
| 기계 | 도커 VM 과 외부 도구가 간헐적으로 돌았다. 단계 시작 load 가 12~28 로 출렁인 실행이 있고 전부 CSV 에 남겼다 |

실행 순서는 `load/results/order-modes-split-*.csv` 와 스크립트 넷에 있다.

완주 직후라 그 틈이 비어 있었다.

## 판정 (잰 뒤에 기준을 바꾸지 않았다)

| # | 기준(#105 원문) | 결과 |
|---|---|---|
| 1 | 행 수 일치 그리고 체크섬 일치, 하나라도 어긋나면 실패 | **일치** |
| 2 | 이중 쓰기 구간 전달 p95 가 평시 5회 중앙값의 1.5배 이내 | 충족 (1305 대 1680 상한, 1.17배) |
| 3 | 각 속도에서 유실 0 · 뒤집힘 0, p95 가 평시 1.5배를 넘는 속도는 못 쓰는 속도 | 5천 · 1만 인정(1.18 · 1.31배), 무제한 기각(6.6배 이상). **균형점 1만 행/초** |
| 4 | 배리어 2초 이내, 잔여 불일치 0 | 충족 (445ms, 잔여 0) |

단계 대표값은 기준 2가 중앙값을 쓰므로 같은 방식(회차 중앙값)으로 읽었다.
가설 네 개(H1 이중 쓰기 가산은 평시 변동 안, H2 균형점 존재, H3 배리어 2초
안, H4 전 과정 유실 · 뒤집힘 0)가 모두 예상대로였다.

## 무엇을 포기했나

- **송신 경로가 INSERT 한 번만큼 느려진다** (건당 p95 1.3ms). 이관 기간에만
  내는 값이다
- **읽음 · 수정 · 삭제 같은 가변 열은 이중 쓰기 범위 밖이다.** 체크섬도 저장
  시점에 정해지는 불변 열만 비교한다. 진짜 컷오버(읽기 전환) 전에 가변 열
  재동기화나 UPDATE 이중화가 따로 필요하고, 이것이 이 실험의 가장 큰 한계다
- **배리어 상한(5초)을 넘기면 송신이 먼저다.** 그 경우 컷오버는 실패하고
  검증이 잡는다. 송신을 영영 막는 것보다 컷오버를 다시 하는 쪽을 골랐다

## 후속: 되돌림 리허설 ([#109](https://github.com/dj258255/joying/issues/109))

"정본이 옛 DB 라 끄면 끝"이 설계로만 있어서 실제로 되돌려 봤다. 백필이 도는
중에(계획은 절반 지점이었으나 측정창 길이 때문에 약 10% 지점에서) 중단을
결정하고, 백필 중단 → 두 노드 재기동(이중 쓰기 끔) → 새 DB 테이블 폐기까지
**25.5초**였다. 전 과정에서 송신 유실 0 · 뒤집힘 0이었고(중단 직전 창과 완료
직후 창 각 400건), 되돌린 뒤 옛 DB 단독으로 정상이다. 재기동 방식이라 직결
클라이언트는 그 사이 재연결이 필요하다. 앞단을 둔 롤링이면 없앨 수 있는
비용이지만 이 지형에서는 재지 않았다.

## 후속: 원격 DB 조건 (같은 이슈)

두 DB 가 같은 기계라는 전제를 toxiproxy 왕복 지연으로 깼다. 비교의 기준선은
프록시만 끼운 지연 0 조건이다(프록시 홉 자체가 이중 쓰기 건당 1.3ms → 3.8ms,
백필 실효 2만 → 1만 행/초를 만든다).

| 왕복 지연 | 이중 쓰기 p95(건당) | 전달 p95 | 백필 실효 |
|---|---|---|---|
| 0ms (프록시만) | 3.8ms | 2,158ms | 10,083행/초 |
| 5ms | 8.1ms | 2,987ms | 5,736행/초 |
| 30ms | 34.6ms | **8,325ms** | 3,347행/초 (60초 측정) |

- 사전 판정 기준(평시 1,120ms 의 1.5배 = 1,680ms) 원문대로 적으면 프록시 0ms
  조건부터 이미 넘는다(2,158ms). 프록시 홉과 측정 시점의 잔여 부하가 섞인
  값이라, 지연의 순수 효과는 같은 세션의 0ms 대비로 본다: 30ms 에서 3.9배
- **판정: 왕복 30ms 급 원격에서는 동기 이중 쓰기를 그대로 못 쓴다.** 건당
  +34.6ms(H2 예상대로 왕복 1회 가산)가 요청당 비용으로 끝나지 않고 방 단위
  직렬 큐에서 누적돼, 몰린 송신 200건의 꼬리를 수 초로 민다(34.6ms × 200건
  ≈ +6.9초, 실측 p95 8.3초와 맞는 크기)
- 후속 선택지는 비동기 미러 + 확인(outbox)이나 배치 미러다. 비동기의 "조용한
  실패" 비용은 그때 다시 잰다
- 30ms 의 15초 백필이 0행이었다. 첫 배치가 15초 안에 못 끝난 것이라 60초로
  늘려 쟀다. 0을 결과로 쓰지 않기 위한 재측정이다

## 아직 하지 않은 것

- **읽기 전환.** 조회 경로를 새 DB 로 돌리는 일은 하지 않았다. 실시간 전달은
  DB 읽기를 지나지 않아 이번 측정에는 안 보이지만, 분리를 끝내려면 남은 반이다
- **가변 열 동기화.** 위의 한계 그대로다
- **원격 조건의 대안(비동기 미러) 실측.** 동기가 기각된 조건에서 비동기의
  지연 이득과 조용한 실패 비용은 재지 않았다
