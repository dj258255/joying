# 결제 버튼을 두 번 누르면 결제가 열 건 생겼다

## 무엇이 문제였나

결제 생성은 이미 있는지를 조회해서 판정하고 있었다. 조회와 삽입 사이에 아무것도 막아
주는 것이 없어서, 동시에 들어온 요청이 둘 다 없다고 읽고 둘 다 넣는다.

응답만 보면 전부 정상이라 눈에 띄지 않는다. 세야 할 것은 응답이 아니라 남은 행이다.

## 잰 조건

| 항목 | 값 |
|---|---|
| 도구 | k6, 같은 순간에 출발하는 16개 가상 사용자 |
| 요청 | `POST /api/v1/payments`, 같은 `rentalHisId` |
| 서버 | 로컬 단일 노드, MySQL 8.0 (기본 격리 수준 REPEATABLE READ) |
| 세는 것 | 응답 성공 건수, 남은 결제 행, 서로 다른 주문번호 개수 |
| 실행 | 설정마다 3회, 매번 결제 행을 비우고 시작 |

실행: `k6 run load/k6/payment-create-race.js`

## 결과

| | 응답 성공 | 남은 결제 행 | 서로 다른 주문번호 |
|---|---|---|---|
| **고치기 전** | 11 / 16 | READY 10 + CANCELED 1 | 11 |
| **고친 뒤** | 16 / 16 | READY 1 | 1 |

3회 모두 같은 수치가 나왔다.

고치기 전에는 대여 하나에 살아 있는 결제가 열 건 붙었다. 하나가 승인되면 나머지 아홉은
READY 로 남아, 나중에 무엇이 진짜 결제인지 알 수 없게 된다.

## 세 겹으로 막았다

한 겹씩 얹으면서 매번 다시 쟀다. 앞의 둘만으로는 수치가 완전히 잡히지 않았다.

| 얹은 것 | 응답 성공 | 남은 결제 행 |
|---|---|---|
| 없음 | 11 | 10 |
| 유니크 제약 | 1 | 1 |
| + 대여 건 잠금 | 2 | 1 |
| + 두 번 누른 것 구분 | 7 | 1 |
| + 잠금 읽기 | 16 | 1 |

### 1. 살아 있는 결제에 유니크 제약

대여 건과 결제 종류를 묶은 값을 열로 두고 유니크를 걸었다. 취소되면 그 값을 비운다.
MySQL 은 유니크 인덱스에서 빈 값을 서로 다른 것으로 보므로, 재시도하며 쌓이는 취소 건은
여럿이어도 된다.

처음 결제와 연장 결제는 같은 대여 건에 함께 있을 수 있어 종류까지 넣었다.

이것만으로 행은 하나가 됐지만 나머지 열다섯은 500 으로 떨어졌다.

### 2. 대여 건을 잠그고 판정

제약에 걸렸을 때 이미 있는 것을 찾아 돌려주려 했는데 되지 않았다.
**flush 가 실패하면 영속성 컨텍스트가 망가져 같은 트랜잭션 안에서는 다시 조회할 수 없다.**
`Entry for instance of Payment has a null identifier` 로 떨어진다.

되돌리려면 트랜잭션을 새로 열어야 한다. 그러지 않고 대여 건을 잠가 애초에 제약까지
가지 않게 했다. 제약은 그대로 두었다. 잠그는 것을 잊은 다른 경로가 생겨도 두 건이 되지
않는다.

여기서 또 하나가 나왔다. Hibernate 는 한 트랜잭션 안에서 INSERT 를 UPDATE 보다 먼저
내보낸다. 옛 결제를 취소하고 새것을 만들면, 새것의 INSERT 가 먼저 나가 아직 비워지지
않은 옛 열쇠와 부딪힌다. 취소를 먼저 반영시켜 해결했다.

### 3. 두 번 누른 것과 나중 재시도를 구분

READY 결제가 있으면 무조건 취소하고 새 주문번호를 만들고 있었다. 그래서 열여섯 번
누르면 주문번호가 열여섯 개 만들어지고 열다섯 개가 버려졌다.

토스는 이미 시도한 적이 있는 주문번호를 다시 받지 않으므로, 사용자가 결제창을 닫았다가
다시 온 경우에는 새 번호가 맞다. 하지만 두 번 누른 것은 다르다. 그 짧은 사이에 결제창을
열어 실패까지 다녀올 수 없으므로 그 주문번호는 아직 토스에 간 적이 없다.

기준을 시간으로 뒀다. 서버는 결제창이 열렸는지 알 방법이 없다. 토스가 알려 주는 것은
승인 결과뿐이고 창을 열었다가 닫은 것은 알려 주지 않는다. 기본값 10초로 두고 설정으로 뺐다.

길게 잡으면 진짜 재시도가 옛 주문번호를 받아 토스에서 거절당하고, 짧게 잡으면 두 번
누른 것이 새 번호를 받아 주문번호가 버려진다.

### 4. 조회도 잠금으로

셋을 다 얹고도 아홉 건이 실패했다. 원인은 격리 수준이었다.

**MySQL 의 기본 격리 수준에서 평범한 조회는 트랜잭션이 처음 읽은 시점의 모습을 계속
본다.** 결제 생성은 회원과 상품을 먼저 읽고 그다음에 대여 건을 잠근다. 잠금은 제대로
걸렸지만, 그 시점에는 이미 스냅숏이 잡혀 있어서 앞선 요청이 만들고 커밋한 결제가 보이지
않았다.

잠금 읽기는 그 규칙에서 빠져 항상 지금 커밋된 것을 본다. 결제 조회를 잠금 읽기로 바꾸자
열여섯 건이 전부 통과했다.

**대여 건을 잠그는 것만으로는 부족하다.** 잠근 뒤에 무엇을 어떻게 읽는지까지 봐야 한다.

## 아직 하지 않은 것

- **승인 경로는 재지 않았다.** `POST /payments/confirm` 은 실 토스 API 를 부르므로
  부하로 돌릴 수 없다. 승인 쪽 동시성은 따로 다뤄야 한다.
- **잠금이 길어질 때를 재지 않았다.** 대여 건 하나를 잠그므로 같은 대여의 결제 생성만
  줄을 서지만, 그 줄이 얼마나 길어질 수 있는지는 재지 않았다.
- **10초 기준을 실제 사용자 행동으로 검증하지 않았다.** 두 번 누르는 간격과 결제창을
  닫았다 돌아오는 간격의 실제 분포를 모른다. 지금은 짐작으로 정한 값이다.
- **연장 결제 경로는 같은 방식으로 확인하지 않았다.** 열쇠에 종류를 넣어 두었지만
  부하로 재지는 않았다.
