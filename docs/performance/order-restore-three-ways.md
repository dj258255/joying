# 순서 복원 셋을 재니 스티키를 버릴 이유가 없었다

순서를 네트워크(스티키 라우팅), 서버(방 단위 중재), 클라이언트(보류 버퍼) 어디서
복원할지 한 지형에서 쟀다. 가설과 판정 기준은 재기 전에
[#91](https://github.com/dj258255/joying/issues/91)에 박아 두었다.

결론부터.

- 셋 다 순서를 지킬 수 있다. 서버 중재는 최악 배치(두 사람이 다른 노드)에서 수신
  뒤집힘 0을 5회 모두 지켰고, 보류 버퍼는 방출 뒤집힘 0이 5회 중 4회였다(1회는
  시작 경계 2건, 아래에)
- 값이 다를 뿐이다. 중재는 잠금 대기(p95 8ms)와 만료 창을, 보류 버퍼는 결번
  대기 설계를 치른다. 이번 부하에서 버퍼 대기는 중앙값 · p95 모두 0ms였다
- 그런데 분산의 지연 이득이 없었다(기준 3 미달). 병목이 노드 밖(공유 Redis ·
  PostgreSQL)에 있어서, 스티키가 강제하는 집중은 이 지형에서 비용이 아니다.
  그래서 기본은 스티키 유지이고, 중재는 스티키가 아플 때(노드 증감이 잦거나
  LB 제약)를 위한 준비된 대안으로 남긴다

## 왜 쟀나

스티키 라우팅은 뒤집힘을 0으로 만들었지만(42~54회 → 0회) 공짜가 아니다. 노드
2 → 3에서 방 602/2,000(30.1%)이 자리를 옮기고, 한 방의 트래픽은 한 노드에
갇히고, 앞단이 방 번호를 알아야 한다. 업계도 갈려 있다. Slack 은 채널 서버가
순서를 중재하고 Discord 는 번호를 믿고 클라이언트가 정렬한다. 우리 지형에서
스티키 말고 다른 두 자리가 얼마짜리인지 몰랐다.

뒤집힘의 원인은 특정돼 있다. 번호 발급(Redis 증가)과 발행(pub/sub)이 별개
호출이라 노드 둘 사이에는 순서가 없다. 서버 중재([#92](https://github.com/dj258255/joying/issues/92))는
그 둘을 방 단위 잠금으로 묶고, 보류 버퍼([#93](https://github.com/dj258255/joying/issues/93))는
받는 쪽이 번호 순으로만 방출한다.

## 잰 조건

| 항목 | 값 |
|---|---|
| 서버 | 같은 기계에서 두 프로세스(8080 · 8081). 저장소는 공유 |
| Redis | 호스트 네이티브(6379) 하나를 두 노드가 공유. 번호 · 발행 · 잠금 전부 여기를 지난다 |
| 도구 | k6, `load/k6/order-modes.js` + `load/k6/lib/holdback.js` |
| 부하 | 쌍 1(방 9001), 두 사람이 각 100건을 몰아서 전송, 합 400건 수신 관찰 |
| 세는 것 | 수신 뒤집힘(기존 정의 그대로), 방출 뒤집힘, 결번 포기, 유실, 왕복 중앙값 · p95 |
| 실행 | 방식마다 5회. 실행별 시작 load 를 CSV `load_before` 열에 기록 |
| 집중 대 분산 | 쌍 10(각 50건, 합 2,000건 수신), 배치 3종 × 3회 |
| 기계 | 도커 VM 과 외부 도구(junie)가 간헐적으로 돌았다. 간섭이 겹친 실행은 아래에 따로 적었다 |

실행: `load/run-order-modes.sh <라벨> 5 ASSIGN=<배치> [HOLD_MS=2000]`
(서버 모드는 `CHAT_ORDERING_MODE` 로 띄운다). 원자료는 `load/results/order-modes-*.csv`.

## 결과: 순서

| 방식 | 배치 | 수신 뒤집힘 (5회) | 방출 뒤집힘 | 결번 포기 | 유실 |
|---|---|---|---|---|---|
| A 스티키(현행) | 같은 노드 | 0 · 0 · 0 · 0 · 0 | — | — | 0 |
| 대조군(아무것도 안 함) | 다른 노드 | 16 · 14 · 16 · 8 · 10 | — | — | 0 |
| B 서버 중재 | 다른 노드 | **0 · 0 · 0 · 0 · 0** | — | — | 0 |
| C 보류 버퍼(HOLD_MS 2s) | 다른 노드 | 40 · 22 · 16 · 18 · 30 | **0 · 2 · 0 · 0 · 0** | 0 | 0 |

- 대조군이 현상을 재현한다. 다른 노드에 갈라 붙이면 400건 중 8~16회 뒤집힌다
- B 는 같은 틈(발급과 발행 사이)을 잠금으로 막아 최악 배치에서도 0이다
- C 의 방출 뒤집힘 2건은 관찰 시작 경계다. 첫 도착으로 기준 번호를 잡는 설계라
  그보다 앞 번호가 늦게 오면 역전 방출이 된다. 실제 화면은 입장할 때 메시지
  목록을 먼저 불러 기준을 아는 상태로 시작하므로 이 경계가 없지만, 그것은 이번에
  재지 않았다. 기준 1 원문대로 C 는 기각하지 않고 **조건부**로 기록한다

## 결과: 지연

| 방식 | 왕복 중앙값(5회) | 왕복 p95(5회) |
|---|---|---|
| A 스티키 | 1413 · 831 · 782 · 545 · 982 | 2355 · 1386 · 1297 · 999 · 1787 |
| 대조군 | 398 · 941 · 343 · 342 · 394 | 755 · 1344 · 663 · 587 · 646 |
| B 중재 | 945 · 671 · 540 · 524 · 501 | 1495 · 1163 · 990 · 1092 · 935 |
| C 버퍼 | 2396 · 309 · 674 · 323 · 417 | 4476 · 562 · 1174 · 647 · 764 |

- **기준 2 충족**: B 의 p95 중앙값 1092ms 는 A 의 p95 중앙값 1386ms 의 1.5배
  이내다. 다만 A 와 B 는 기계 상태가 달랐다(A 는 직전 벤치 잔여 load 11~14,
  B 는 load 4~5). 그래서 "B 가 A 보다 빠르다"고는 말하지 않는다. 기준이 요구한
  "1.5배 이내"까지만 말한다
- B 의 중재 비용 자체는 서버 지표로 쟀다. 잠금 대기 p50 3.5~3.7ms, p95
  7.6~8.1ms(노드별), 잠금 타임아웃 0. 왕복 수백 ms 에 비해 한 자릿수 ms 다
- C 의 버퍼 대기는 중앙값 · p95 모두 0ms 였다. 역전된 메시지의 다음 번호가
  밀리초 안에 뒤따라 도착해 쥐고 있을 시간이 없었다. 방출 기준 왕복과 수신 기준
  왕복이 같은 분포다. 대가가 없었다는 뜻이 아니라, 이 부하의 역전 간격이 버퍼
  상한(2초)보다 훨씬 짧았다는 뜻이다
- A 1회차(p95 2355)와 C 1회차(p95 4476)는 시작 load 14~16 의 간섭이 겹쳤다.
  CSV 에 그대로 남겼고 중앙값 비교로 흡수했다

## 결과: 집중 대 분산

스티키가 강제하는 "한 노드 집중"이 얼마짜리인지 쌍 10개로 쟀다. 같은 총
송신률에서 배치만 바꿨다.

| 배치 | 뒤집힘(3회 합) | p95 3회 | p95 중앙값 |
|---|---|---|---|
| 집중(전부 1번 노드) | 0 | 1280 · 1495 · 1514 | 1495ms |
| 쌍별 분배(방 홀짝, 스티키의 정상 모습) | 0 | 1201 · 1507 · 1288 | 1288ms |
| 교차 분산(두 사람이 다른 노드) | 342 | 1557 · 2005 · 1402 | 1557ms |

- **기준 3 미달**: 분산이 집중보다 20% 이상 낮지 않다. 쌍별 분배가 13.8% 낮고
  교차 분산은 오히려 높다
- 기준 3 원문대로 **병목이 노드 밖에 있다**고 기록한다. 이 지형에서는 모든
  메시지가 같은 Redis(번호 · 발행)와 같은 PostgreSQL(저장)을 지나므로, 노드를
  갈라도 병목은 그대로다. 분산은 순서 비용만 내고 지연 이득이 없다. 이것이
  스티키 유지의 근거다
- 간섭 기록: 쌍별 분배 2회차 시작 load 46(외부 도구), 교차 1회차 load 17.
  CSV 에 남겼다

## 판정 (잰 뒤에 기준을 바꾸지 않았다)

| # | 기준(#91 원문) | 결과 |
|---|---|---|
| 1 | B 수신 뒤집힘 0, C 방출 뒤집힘 0 그리고 결번 포기 0. 한 번이라도 어기면 기각 또는 조건부 | B 성립(5/5). C 조건부(4/5, 1회 시작 경계 2건, 포기 0) |
| 2 | B 의 p95 가 A 대비 1.5배 이내면 수용 | 충족(1092 대 1386, 기계 조건 차이는 위에) |
| 3 | 분산 p95 가 집중 대비 20% 이상 낮으면 집중 비용 실재 | 미달(13.8%). 병목이 노드 밖. 스티키 유지 근거 |
| 4 | 전 방식 유실 0, 어기면 그 실행 무효 | 전 24회 유실 0 |

종합하면 **기본은 스티키 유지**다. 분산이 지연을 벌지 못하므로 스티키의 집중
강제는 이 지형에서 비용이 아니고, 남는 스티키 비용은 방 이동(30.1%)과 LB
결합뿐이다. 그 둘이 아파지는 조건(노드 증감이 잦다, 앞단을 바꿔야 한다)이 오면
B 를 설정 하나(`CHAT_ORDERING_MODE=arbiter`)로 켠다. 그때 치르는 값은 잠금
대기 p95 8ms 와, 잠금 만료(2초) 때 순서 보장이 깨질 수 있는 창이다. 그 창은
없앨 수 없고 `chat.order.lock.timeouts` 로 셀 수만 있다.

## 재는 자리를 이번에도 틀렸다

- 처음 돌린 안읽음 측정은 캐시 삭제를 **아무도 안 쓰는 Redis** 에 날렸다.
  compose 의 Redis 는 포트 변수가 비어 32835 로 발행됐고, 호스트 6379 에는
  이 기계에 따로 깔린 redis-server 가 살고 있었다. 서버는 줄곧 호스트 쪽을
  썼다. 상황 33(같은 포트의 남의 앱)과 같은 유형이다. 두 노드가 같은 Redis 를
  공유했으므로 이 문서의 순서 · 지연 측정은 유효하고, 조건 표의 Redis 줄을
  사실대로 고쳤다. 안읽음 측정은 다시 쟀다([unread-two-ways.md](unread-two-ways.md))
- 재접속 폭주 측정도 기준선을 한 번 오염시켰다. 자세한 것은
  [reconnect-herd.md](reconnect-herd.md)에

## 아직 하지 않은 것

- **실제 화면의 보류 버퍼.** C 는 k6 관찰자에 구현해 쟀다. 화면(ChatContext)은
  번호 재정렬까지만 있고 결번 감지가 없다. C 를 채택하는 조건이 오면 입장 시
  기준 번호 동기화와 함께 화면에 구현하고 화면 경로로 다시 재야 한다
- **잠금 만료 창의 실측.** 임계 구역이 2초를 넘겨 잠금이 먼저 풀리는 상황은
  저장소를 느리게 만들어야 재현된다. toxiproxy 로 만들 수 있지만 이번 범위
  밖이다
- **노드 3대 이상.** 중재의 잠금 경쟁은 한 방에 둘뿐이라 약했다. 1:1 이 아닌
  도메인이라면 결과가 다를 수 있다
- **방 이동 비용과 순서의 상호작용.** 노드 증감 순간에 스티키는 방을 옮기고
  중재는 그대로다. 그 순간의 전달 공백은 재지 않았다
