# 안읽음을 세는 두 방법을 재니 캐시의 값이 생각보다 작았다

이 서비스는 안읽음을 두 겹으로 센다. Redis 카운터(`unread:{방}:{사람}`, TTL
7일)가 캐시, `lastReadSequence` 초과 집계(DB count)가 정본이다. Slack 은 커서
차이로만 계산한다. 어느 쪽이 비용을 내는지 숫자로 적은 적이 없어서 쟀다.
가설(H5)과 판정은 [#96](https://github.com/dj258255/joying/issues/96)에 먼저
적었다.

결론부터.

- 쓰기 증폭은 예상대로다. 메시지 1건당 Redis 쓰기 2회(번호 1 + 안읽음 1).
  카운터를 버리면 1회가 준다
- **H5 기각.** 캐시 히트 5.8ms 대 미스(DB 집계) 18.1ms 로 3.1배다. 예상한 "한
  자리 수 이상(10배)" 차이가 아니다. 5만 건 방에서도 커서 집계가 18ms 라
  캐시 없이 견딜 수준이다
- 사전 판정대로 **카운터 캐시의 값이 작다**고 기록한다. 캐시가 틀릴 수 있는
  경로(멱등 재전송의 이중 증가 [#99](https://github.com/dj258255/joying/issues/99),
  축출로 인한 번호 중복 [#100](https://github.com/dj258255/joying/issues/100))를
  안고 갈 만큼의 이득이 아니므로, #99 를 고칠 때 카운터를 커서 단일로 줄이는
  선택지를 같이 검토한다

## 잰 조건

| 항목 | 값 |
|---|---|
| 서버 | 1대(8080), 현행(node) 모드 |
| 바쁜 방 | 방 9501에 메시지 50,000건 시드, 읽은 지점(lastReadSequence)은 10으로 고정해 집계가 전체에 가깝게 |
| 쓰기 증폭 | 실제 경로(STOMP)로 40건을 보내고 Redis 키 값의 전후 차이로 센다 |
| 조회 | 방 목록 GET `/api/v1/chat-rooms`(안읽음이 실리는 경로) 30회씩. 미스는 반복마다 카운터 키를 지워 DB 집계를 태운다 |
| Redis | 호스트 네이티브(6379). 아래 "재는 자리" 참고 |

실행: `load/run-unread-two-ways.sh 30 50000` (원자료 `load/results/unread-two-ways*.csv`)

## 결과

쓰기 증폭 (메시지 40건):

| 항목 | 증가량 |
|---|---|
| `chat:sequence:{방}` (번호) | +40 |
| `unread:{방}:{받는 사람}` (카운터) | +40 |

메시지 1건이 Redis 증가 2회를 만든다. 번호는 순서의 근거라 뺄 수 없고, 카운터가
추가분이다.

조회 지연 (각 30회):

| 경로 | 중앙값 | p95 |
|---|---|---|
| 캐시 히트 | 5.8ms | 11.1ms |
| 캐시 미스(DB 집계 + 다시 채움) | 18.1ms | 25.3ms |

## 왜 집계가 느리지 않나

`countBy…SequenceGreaterThanAndSenderIdNot` 이 `(chat_room_id, sequence)`
인덱스의 범위를 세는 쿼리다. 5만 행을 세도 수 ms 대다. 안읽음이 수십만 건
쌓이는 방이 아니라면 집계 자체가 병목이 되기 어렵다.

## 재는 자리를 또 틀렸다

첫 측정은 히트 6.0ms 대 미스 4.7ms 로 차이가 없었다. 미스를 만들려고 지운
캐시 키가 **아무도 안 쓰는 Redis** 에 있었기 때문이다. compose 의 Redis 는 포트
변수가 비어 32835 로 발행됐고, 호스트 6379 에는 이 기계에 따로 깔린
redis-server 가 살고 있었다. 서버는 줄곧 호스트 쪽을 썼으므로 "미스" 30회가
전부 히트였다. 상황 33(같은 포트의 남의 앱)과 같은 유형이고, 지우는 자리를
호스트 쪽으로 바꿔 다시 쟀다.

쓰기 증폭도 처음에는 Redis MONITOR 로 세려 했는데, 비TTY 에서 출력이 버퍼에
쥔 채 종료돼 번번이 1줄만 남았다. 명령 스트림 대신 **키 값의 전후 차이**로
바꿨다. 증가 연산은 결과가 값에 그대로 쌓이므로 이쪽이 유실될 수 없다.

## 아직 하지 않은 것

- **수십만 건 방.** 5만 건 기준이다. 집계 18ms 가 어디까지 선형인지 재지 않았다
- **방 목록에 방이 수백 개인 사용자.** 여기서는 방 5개였다. getBatch 가 방마다
  미스면 집계가 방 수만큼 돈다
- **카운터 제거의 실제 효과.** 커서 단일로 줄이는 변경은 #99 와 함께 설계부터
  해야 한다. 이 문서는 그 결정의 입력이다
