# 지금 알게 된 것으로 다시 고른다면

## 지금 무엇을 쓰고 있나

저장소가 넷이다.

| 저장소 | 무엇에 |
|---|---|
| MySQL | 회원·상품·대여·결제·정산·원장 |
| MongoDB | 채팅 메시지 |
| Redis | 안읽음 집계, 접속 상태, 메시지 번호 발급, 서버 간 전달 |
| Elasticsearch | 상품 검색과 자동완성 |

팀 프로젝트에서 여섯 명이 아는 것을 고른 결과다. 그 자체로 잘못된 판단은 아니다.

다만 이 규모에 **장애 지점이 넷**이다. 리팩토링하며 그것이 실제로 드러났다.

- Redis 를 끊으니 채팅이 통째로 섰다. 번호 발급이 아니라 연결 단계에서 먼저 막혔다
- Elasticsearch 가 죽으면 검색이 500 으로 떨어진다. 대체 경로가 만들어져 있는데 이어져 있지 않다
- MongoDB 와 MySQL 에서 **같은 종류의 함정을 각각 한 번씩** 밟았다

## 각각에서 부딪힌 것

### MySQL: 없는 기능을 데이터 모델로 흉내 냈다

결제 경합을 고칠 때 "살아 있는 결제는 대여 건과 종류마다 하나"라는 제약이 필요했다.

MySQL 에는 조건부 유니크 인덱스가 없다. 그래서 `active_key` 열을 새로 만들고, 취소할 때
`null` 로 비우고, 그 규칙을 엔티티 안에 심었다. 유니크 인덱스가 빈 값을 서로 다른 것으로
본다는 성질에 기대는 방식이다.

PostgreSQL 이면 한 줄이다.

```sql
CREATE UNIQUE INDEX uk_payment_active ON payment (rental_his_id, payment_type)
  WHERE status <> 'CANCELED';
```

열도 필요 없고 취소할 때 비울 것도 없다.

### MySQL: 격리 수준 때문에 잠금을 두 겹으로 걸었다

같은 결제 경합에서, 대여 건을 잠갔는데도 앞선 요청이 커밋한 결제가 보이지 않았다.
MySQL 의 기본 격리 수준에서 평범한 조회는 트랜잭션이 처음 읽은 시점의 모습을 계속 본다.
결제 생성은 회원과 상품을 먼저 읽으므로 잠글 때는 이미 시점이 잡혀 있었다.

결제 조회까지 잠금 읽기로 바꿔서야 통과했다.

PostgreSQL 의 기본 격리 수준에서는 평범한 조회가 매번 지금 커밋된 것을 본다.
**이 문제 자체가 생기지 않는다.**

### MongoDB: 관계가 없는 게 아니라 이미 있었다

코드 주석에 "쌓이기만 하고 관계를 맺지 않아 MongoDB 에 둔다"고 적혀 있다. 그때는 맞는
판단이었다.

그런데 이번에 실제로 한 일을 보면 이렇다.

- 방 안에서 순서를 정할 번호를 붙였다
- 같은 전송을 한 번만 저장하도록 조건부 유니크 인덱스를 걸었다
- 4,425건에 번호를 채우는 백필을 만들었다
- 답장 대상을 한 번에 가져오도록 일괄 조회로 바꿨다
- 읽은 지점을 참여자에 번호로 들게 했다

메시지는 방에 속하고, 답장은 다른 메시지를 가리키고, 읽은 지점은 참여자에 붙는다.
**관계가 없는 것이 아니라 이미 있었다.** 그것을 문서 저장소에서 손으로 관리하고 있었다.

### MongoDB: sparse 가 복합 유니크에서 이름만 맞았다

전송 식별자에 유니크를 걸 때 `sparse` 를 썼다. `sparse` 는 인덱스 키 중 하나라도 값이
있으면 색인하므로, 복합 인덱스에서는 방 번호만 있어도 문서가 들어가고 식별자 없는 두 건이
부딪혔다. 조건부 인덱스로 바꿔 해결했다.

**MySQL 에서 부분 인덱스가 없어 겪은 것과 같은 종류의 문제를 저장소를 옮겨 가며 두 번
겪었다.**

### Elasticsearch: 무거웠던 것은 도구가 아니라 설정이었다

힙을 안 잡아 4.19GiB 를 쓰고 있었다. 512MB 로 잡으니 905MiB 가 됐다.
자세한 것은 [검색 엔진 선택](search-engine-choice.md).

## 다시 고른다면

**PostgreSQL 하나로 시작한다.**

| 시점 | 저장소 | 넣는 근거 |
|---|---|---|
| 시작 | PostgreSQL | 거래·채팅·상품 전부 |
| 서버를 두 대로 늘릴 때 | + Redis | 노드를 넘는 전달이 필요해진다 |
| 검색이 아쉬워질 때 | + Elasticsearch | 형태소 분석·오타 교정 |

### 왜 PostgreSQL 인가

- **조건부 유니크 인덱스**가 있다. 위의 두 우회가 모두 사라진다
- **기본 격리 수준**이 읽을 때마다 지금 커밋된 것을 본다. 잠금을 두 겹으로 걸 이유가 없다
- 채팅 메시지는 파티셔닝으로 감당한다. "쌓이기만 한다"는 성질은 월별로 자르면 된다
- `JSONB` 가 있어 문서 저장소가 필요한 자리를 한 저장소 안에서 해결한다

### 검색은 나중에 넣는다

PostgreSQL 은 한국어 전문검색 설정을 기본 제공하지 않는다. 필요해지면 PostgreSQL 을
억지로 쓰지 말고 Elasticsearch 를 그냥 추가한다. **저장소를 늘리는 판단을 그 시점의
근거로 한다.**

### Redis 도 같다

서버가 한 대면 Spring 내장 브로커로 충분하다. 두 대로 늘리는 순간 넣는다.

## 지금 옮기는 것은 다른 질문이다

그린필드 판단과 지금 옮길지는 다르다. 옮기면 이번에 만든 것 — 메시지 번호, 멱등, 백필,
읽은 지점, 방 단위 라우팅 — 을 전부 다시 검증해야 한다.

그 비용을 알고 옮기기로 했다. [이행 기록](../migration/postgresql.md)에 남긴다.
