# 몰린 송신을 들어오는 자리에서 거절하니 다른 방이 밀리지 않았다

[느린 소비자 측정](slow-consumer.md)의 결론은 "피해자를 민 것은 느림이 아니라
동시 송신 부하 자체"였다. 그 제어를 회원당 토큰 버킷(초당 5건 · 버스트 10)으로
만들고, 폭주를 막는지와 사람 속도의 대화는 안 걸리는지를 쟀다. 가설과 판정
기준은 [#118](https://github.com/dj258255/joying/issues/118)에 먼저 적었다.

결론부터.

- **폭주가 남의 방을 못 민다.** 서른 방 × 1,200건(30ms 간격) 폭주에서 피해자
  전달 p95 가 제한 없이는 16.6~17.5초, 제한을 켜면 21~34ms 다. 기준선(25~37ms)과
  같은 수준으로 돌아온다
- **사람은 안 걸린다.** 300ms 간격(사람 속도)의 대화 1,000건에서 거절 0,
  p95 25~29ms 로 기준선 그대로다
- **거절의 회계가 정확히 맞는다.** 폭주 시도 36,000건 = 저장 5,910 + 거절
  30,090. 방당 저장 197건은 버스트 10 + 초당 5건 × 36.9초의 토큰 산수 그대로다.
  거절은 조용한 드롭이 아니라 지표로 세고 보낸 사람에게 알린다

## 어디서 막는가 (선택지)

- **거절(채택)**: 방 직렬 큐에 넣기 전에 끊는다. 큐에 들어간 뒤는 이미 자원을
  먹는다. 비용은 폭주 송신자의 사용자 경험이고, 사람 속도는 걸리지 않게 값을 잡는다
- 지연(인바운드 처리를 늦춤): 인바운드 스레드가 묶여 다른 세션으로 전파된다.
  느린 소비자 문제의 인바운드판이라 기각
- 연결 끊기: 재접속 폭주를 부른다. 기각

## 잰 조건

| 항목 | 값 |
|---|---|
| 서버 | 1대(8080), 제한은 `joying.chat.inbound.rate-per-second`(0이면 끔) · `burst` 로 교체 기동 |
| 피해자 | 정상 쌍 5(방 9401~9405), 각 50건을 300ms 간격(사람 속도)으로 교환 |
| 폭주 | 먹이 30방(9421~9450) × 1,200건(30ms 간격, 약 33건/초) + 정상 수신 30명 |
| 조건 | 기준선(피해자만) · 폭주 모두 제한 off 와 on(5건/초 · 버스트 10)에서 각 2회 |
| 거절 수 | /actuator/prometheus 의 `chat_message_send_rejected_total` 전후 차이 |
| 시작 load | 10.5~20.5 (실행별 기록. 외부 프로세스 상주 중의 측정이라 절대값보다 조건 간 비교가 기준) |

실행: `load/run-inbound-backpressure.sh baseline|flood <태그>`
(원자료 `load/results/backpressure-*.json`)

## 판정 (잰 뒤에 기준을 바꾸지 않았다)

| 가설 · 기준(#118 원문) | 결과 |
|---|---|
| H8: 폭주를 제한 off 는 기준선 2배 초과로 밀고, on 은 2배 이하로 돌린다 | **지지** (off 약 590배, on 0.8~1.2배) |
| H9: 사람 속도의 대화는 제한 on 에서 거절 0 | **지지** (1,000건 거절 0, p95 동급) |
| 거절 지표 = 시도 - 저장 | **일치** (36,000 = 5,910 + 30,090, 2회 모두 같은 값) |
| 전 조건 피해자 유실 0 | on 은 충족. **off 폭주는 40 · 56건이 관측 창(40초) 안에 못 왔다.** p95 가 17초면 꼬리는 창을 넘는다. 도착하지 않은 것과 유실은 이 측정으로 구분되지 않아 그대로 적는다 |

둘 다 지지라 사전 기준대로 기본값 on(초당 5건 · 버스트 10)으로 둔다.

## 왜 그런가

- **거절이 정확히 토큰 산수인 이유**: 먹이는 초당 33건으로 밀고 버킷은 초당
  5건씩 찬다. 36.9초 동안 방당 10(버스트) + 184(충전) = 197건이 통과하고
  1,003건이 거절된다. 30방이면 5,910 대 30,090. 결정적이라 재현마다 같은 값이다
- **피해자가 안 밀리는 이유**: 폭주의 피해 경로는 저장(같은 DB) · 발행(같은
  Redis) · 전달(공유 풀)의 공유 자원이었다. 들어오는 양 자체가 1/6 로 줄면
  공유 자원의 줄이 생기지 않는다
- **지연 대신 거절인 이유**: 막히는 자리를 클라이언트 쪽 경계(명시적 실패)로
  밀어낸다. 서버 안에서 기다리게 하면 그 대기가 새 공유 자원(스레드 · 큐)을
  만든다

## 대가

- 폭주 송신자(봇 · 스크립트)의 초과분은 명시적으로 실패한다. 클라이언트는
  `/user/queue/errors` 의 SEND_RATE_LIMITED 와 clientMessageId 로 어느 전송이
  거절됐는지 알고 재시도를 조절할 수 있다
- 거절 알림 자체도 outbound 를 쓴다. 이번 측정(초당 수백 건 거절)에서는 피해가
  없었지만, 더 큰 폭주에서는 알림 샘플링이 필요할 수 있다
- 버킷 맵은 회원 수만큼 자란다. 수십만 회원까지는 맵 하나로 충분하고 그 너머는
  TTL 있는 저장소로 옮길 일이다

## 아직 하지 않은 것

- **값의 근거는 사람의 상한뿐이다.** 초당 5건 · 버스트 10은 1:1 타이핑 상한의
  여유분이다. 이미지 연속 전송 같은 정상 사용이 걸리는지는 화면 경로로 재지 않았다
- **다중 노드.** 버킷이 노드 안에 있어 두 노드에 반씩 붙으면 상한이 2배가 된다.
  스티키 라우팅이 회원을 한 노드에 모으는 동안은 성립하고, 그 전제가 깨지면
  Redis 버킷으로 옮겨야 한다
- **제한 off 폭주의 창 내 미도착 40~56건.** 늦게라도 전부 오는지(전달 완결성)는
  창을 늘려 따로 재야 한다
