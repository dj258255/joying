# 읽지 않는 수신자 서른 명도 남의 방을 못 밀었다

수신이 느린 클라이언트가 같은 노드 다른 방의 전달을 미는지 쟀다. Discord 는
2021년에 느린 클라이언트 하나의 TCP 버퍼가 구독 스레드를 막아 힙이 80GB 까지
자라는 장애를 겪었다. 우리 지형(Spring 내장 브로커)에서 같은 일이 생기는지,
가설과 판정 기준을 [#111](https://github.com/dj258255/joying/issues/111)에
먼저 적고 쟀다.

결론부터.

- **느린 수신자는 격리된다.** 소켓을 읽지 않는 수신자가 1명이어도 30명이어도
  다른 방의 전달 p95 에 추가 효과가 없었다. 세션마다 따로 두는 전송
  버퍼(decorator)가 전파를 끊는다
- **서버 보호는 작동한다.** 읽지 않는 수신자 30명 전원이 50~100초 사이에
  전송 시간 상한으로 끊겼다. 다만 상한을 20초에서 2초로 조여도 끊김 시점이
  같았다. 검사가 다음 전송 시도 시점에만 일어나기 때문이다
- **피해자를 민 것은 느림이 아니라 동시 송신 부하 자체였다.** 서른 방에
  36,000건을 몰아 보내는 조건은 수신자가 정상이어도 다른 방 p95 를
  10.5배(1.1초 → 12.1초) 밀었다. 유실은 전 조건 0, 밀리는 것과 깨지는 것은
  여기서도 다른 축이었다

## 잰 조건

| 항목 | 값 |
|---|---|
| 서버 | 1대(8080). 전파는 노드 안 문제라 한 대로 잰다 |
| 피해자 | 정상 쌍 5(방 9401~9405), 각 50건 주고받으며 전달 왕복 측정 |
| 느린 수신자 | 소켓을 읽지 않는 클라이언트(load/clients/stalled-receiver.py) 1명 또는 30명, 방 9421~ |
| 먹이 | 느린 방마다 발신자가 1,200건(약 1.2KB짜리)을 30ms 간격으로 송신 |
| 보호 설정 | 현행(전송 20초 · 버퍼 512KB) 대 조임(2초 · 64KB), 환경변수로 교체 |
| 실행 | 조건마다 2회(1명 조건은 1회), 시작 load 4.2~8.1 을 각 실행에 기록 |

실행: `ROLE=victims|receivers|feeders k6 run load/k6/slow-consumer.js` 와
읽지 않는 클라이언트를 함께 띄운다. 원자료는 스크립트와 같은 이름의 요약 JSON.

## 판정 (잰 뒤에 기준을 바꾸지 않았다)

| 가설 · 기준(#111 원문) | 결과 |
|---|---|
| H1: 1명은 못 민다 (기준: 피해자 p95 가 기준선 2배 미만) | **지지** (0.7배) |
| H2: 30명이 모이면 민다 | **기각.** 30명 조건은 2배를 넘었지만(9.4배), 느림 없는 대조군(정상 수신 30)이 같은 수준(10.5배)이었다. 민 것은 느림이 아니라 송신 부하다 |
| H3: 상한에서 끊기고, 조이면 더 일찍 끊긴다 | 절반만. 전원 끊김(50~100초)은 확인, **조임의 효과는 없었다**(시점 동일) |
| 전 조건 피해자 유실 0 | 충족 |

## 왜 그런가

- **격리의 구조**: 전송은 세션마다 버퍼를 따로 두는 데코레이터를 지나므로,
  느린 세션 하나가 쥐는 공유 자원은 나가는 채널 풀의 스레드 1개뿐이다(풀
  10~50). Discord 사례처럼 구독 처리 스레드를 여럿이 공유하는 구조가 아니라
  전파 경로가 없다. 기반 구조가 결과를 설명한다
- **조임이 소용없던 이유**: 서버 로그가 말해 준다.
  `Send time 19978ms ... exceeded the allowed limit 2000` — 상한이 2초인데
  19초가 지나서야 끊었다. 상한 검사는 다음 메시지를 보내려는 시점에만
  일어나므로, 전송이 한 번 막히면 다음 시도가 올 때까지 상한이 몇 초든
  똑같이 기다린다. 끊김 시점을 지배하는 것은 상한 값이 아니라 전송 시도
  간격이다
- **10.5배의 정체**: 느린 소비자 실험이 만든 혼동 변수였다. 서른 방에
  36,000건을 쏟는 먹이 자체가 저장(같은 DB) · 발행(같은 Redis) · 전달(공유
  풀)을 지나며 다른 방을 민다. 재접속 폭주 실험에서 본 동시 송신 1.5초의
  확장판이고, 인바운드 쪽 백프레셔(송신 속도 제한)가 다음 과제라는 뜻이다

## 재는 자리를 세 번 틀렸다

- **대역폭 제한 프록시는 느린 소비자가 아니다.** toxiproxy 로 수신을 2KB/s 로
  조였더니 보호가 영영 발동하지 않았다. 프록시가 서버 쪽 데이터를 자기 버퍼로
  대신 읽어 주므로 서버의 TCP 는 막히지 않는다. k6 도 수신을 항상 읽는다.
  그래서 소켓을 읽지 않는 클라이언트를 직접 만들었다
- **k6 의 VU 번호는 시나리오를 넘어 전역이다.** 역할 셋을 한 프로세스에 섞고
  없는 속성(idInScenario)으로 역할 안 번호를 구하려다 방 번호가 전부 깨져
  피해자 수신이 0이 된 실행들을 버렸다. 역할별 별도 프로세스로 다시 쟀다
- **부하가 구독 등록을 밀면 그 사이 메시지는 영영 못 받는다.** 구독 직후
  2초만 기다리고 송신을 시작했더니 한 방향 100건이 통째로 빠지는 실행이
  나왔다. 대기를 8초로 늘려 통제했지만, 이 현상 자체가 재접속 복구(after=번호
  조회)가 필요한 이유의 실측이다

## 아직 하지 않은 것

- **인바운드 백프레셔.** 피해자를 민 진짜 범인(동시 송신 부하)의 제어는 송신
  속도 제한이나 수용 거절의 영역이고, 무엇을 버릴지의 트레이드오프가 따로 있다
- **끊김을 더 일찍 만드는 길.** 상한 검사 주기를 바꾸는 것은 프레임워크 내부라
  비용이 크다. 하트비트 기반 감지 같은 대안은 설계만 있다
- **운영 지표.** 끊긴 세션 수를 Prometheus 로 내보내는 일은 하지 않았다
