# 실제 지형으로 다시 재니 열 배 나빴다

## 앞선 실험이 이 서비스의 모습이 아니었다

두 노드 실험에서 "보내는 사람을 갈라 붙이면 18회 중 1회, 200건 중 4회 뒤집힌다"고 적었다.
드물다고 봤다.

그 실험은 **한 사람이 연결 여덟 개로 동시에 보내는** 상황이었다. 이 서비스는 1:1 이다.
방은 상품과 구매자와 판매자로 유일하고(`uk_chat_room_product_buyer_seller`) 참여자는 둘로
고정된다. 여덟이 한 방에 동시에 말하는 일은 일어나지 않는다.

**드물다는 판단이 잘못된 지형에서 나온 것이었다.**

## 다시 잰 조건

| 항목 | 값 |
|---|---|
| 구매자 | 1번 노드(8080)에 붙어 100건 전송, 동시에 수신 |
| 판매자 | 2번 노드(8081)에 붙어 100건 전송, 동시에 수신 |
| 세는 것 | 각자 받는 순서에서 번호가 뒤로 간 횟수 |
| 실행 | 5회 |

1:1 이므로 두 사람 다 보내면서 받는다. 한쪽만 관찰자로 두면 실제 모습과 다르다.

이 배치가 이 서비스에서 가능한 가장 나쁜 경우다.

실행: `k6 run load/k6/one-to-one-two-node.js`

## 결과

| 두 사람이 붙은 곳 | 뒤집힘 (400건 중) |
|---|---|
| **같은 노드** | 0 · 0 · 0 |
| **다른 노드** | 42 · 48 · 54 · 48 · 4 |

사라진 메시지는 양쪽 모두 0건이다.

**10퍼센트가 넘는다.** 앞선 실험에서 본 "18회 중 1회"와는 다른 수치다.

같은 노드에서 0이 나온다는 것이 원인을 못박는다. 두 노드가 각자 Redis 에 발행하는 구간
말고는 달라진 것이 없다.

### 0 을 보이게 만들어야 했다

처음에는 같은 노드 실행에서 뒤집힘 항목이 아예 표에 뜨지 않았다. 한 번도 증가하지 않은
계수기는 k6 가 표에서 뺀다.

**뜨지 않는 것과 0 인 것을 구분할 수 없었다.** 문턱값을 걸어 0 이어도 뜨게 했다.

## 왜 갈리는가

번호는 Redis 증가 연산 하나가 정하므로 어느 노드에서 발급해도 유일하고 순서가 있다.

그다음이 다르다. 1번 노드가 41번을 발행하는 것과 2번 노드가 42번을 발행하는 것 사이에는
아무 순서가 없다. 각 노드 안에서는 방 단위로 한 줄을 세워 두었지만, **그 줄은 노드마다
따로 있다.**

## 무엇을 할 수 있나

한 방의 두 사람을 같은 노드로 모으면 사라진다. 1:1 이라 이것이 특히 쉽다.

- 방 하나에 두 명뿐이라 한 노드로 모아도 쏠림이 작다
- 방 번호로 노드를 고르면 되고, 그 값은 연결할 때 이미 안다
- 여러 방에 동시에 붙어 있는 사람은 방마다 다른 노드에 붙는다. 방끼리는 순서를 지킬
  이유가 없으므로 문제가 되지 않는다

다만 이것은 웹소켓 연결을 방 번호로 라우팅하는 장치가 필요하다. 지금은 없다.

## 아직 하지 않은 것

- **방 기준 라우팅을 만들지 않았다.** 재서 근거를 만든 데까지다.
- **노드가 셋 이상일 때를 재지 않았다.**
- **한 사람이 기기를 여럿 쓸 때를 재지 않았다.** 같은 사람이 두 노드에 붙으면 1:1 이어도
  발행이 갈린다.
- **같은 기계에서 두 프로세스를 띄웠다.** 떨어진 두 기계 사이의 지연은 더 크고, 어긋남도
  그만큼 커질 수 있다.
