# 저장소가 느려지거나 끊길 때 무엇이 무너지는가

## 왜 했나

부하를 넣어 순서를 맞춰 놓았지만, 그것은 전부 정상일 때의 이야기다. 실제로 무너지는
자리는 저장소가 느려지거나 끊길 때다.

번호를 Redis 에서 받아 MongoDB 에 저장한다. 둘 중 하나가 늦거나 끊기면 번호와 저장이
어긋날 수 있다. 그것을 짐작하지 않고 직접 만들어 봤다.

## 어떻게 만들었나

저장소 앞에 Toxiproxy 를 두고 앱이 프록시를 보게 했다.

```
load/toxiproxy/setup.sh up
POSTGRES_PORT=25432 REDIS_PORT=16381 ./gradlew bootRun
load/toxiproxy/setup.sh latency 300
k6 run load/k6/message-order.js
```

부하는 앞의 실험과 같다. 발신자 8명이 각 25건, 총 200건.

## 결과

저장소를 PostgreSQL 로 옮긴 뒤 같은 조건으로 다시 쟀다.

**PostgreSQL** (지금)

| 주입한 것 | 도착 | 뒤집힘 | 왕복 중앙값 |
|---|---|---|---|
| 없음 | 200 / 200 | 0 | 1.22s |
| 응답 300ms(±100) 지연 | **70 / 200** | 0 | **1분 28초** |
| 연결 30% 확률로 끊김 | 200 / 200 | 0 | — |

**MongoDB** (옮기기 전)

| 주입한 것 | 도착 | 뒤집힘 | 왕복 중앙값 |
|---|---|---|---|
| 없음 | 200 / 200 | 0 | 1.67s |
| 응답 300ms(±100) 지연 | 200 / 200 | 0 | 1분 4초 |
| 연결 30% 확률로 끊김 | 200 / 200 | 0 | — |
| Redis 끊김 | 0 | — | — |

**지연을 넣었을 때 PostgreSQL 이 더 무겁다.** 왕복 중앙값이 1분 4초에서 1분 28초가 됐고,
3분을 기다려도 200건 중 70건만 도착했다.

한 건을 저장하는 데 왕복이 더 많기 때문이다. 문서 저장소는 한 번에 넣지만 관계형은
트랜잭션을 열고 넣고 커밋한다. 각 왕복마다 300ms 가 붙는다.

방 하나를 한 줄로 세운 것이 여기서 그대로 곱해진다. 200건이 차례로 기다리므로 왕복이
늘어난 만큼 줄 전체가 길어진다.

## 지연 300ms 가 왕복 64초가 됐다

가장 눈에 띄는 수치다. 저장소가 300ms 느려졌을 뿐인데 왕복 중앙값이 1.67초에서 64초로
밀렸다.

방 하나의 메시지를 한 줄로 세웠기 때문이다. 200건이 한 줄에서 차례로 처리되고 각각
300ms 를 기다리면 마지막 것은 60초 뒤에 나간다. 순서를 지키려고 만든 줄이, 저장소가
느려지는 순간 그대로 대기열이 된다.

**순서를 얻은 값이 정상일 때는 지연 세 배였고, 저장소가 느려질 때는 40배가 된다.**
줄을 세우지 않았다면 200건이 동시에 밀려 각자 300ms 만 기다렸을 것이다. 대신 순서는
없다.

이것은 고칠 대상이라기보다 이 설계가 어디서 비싸지는지를 보여 주는 수치다. 줄을 잘게
쪼개면 지연은 줄고 순서는 다시 흔들린다.

## 연결이 30% 끊겨도 번호에 빈 자리가 없었다

번호를 받은 뒤 저장이 실패하면 그 번호는 쓰이지 않고 버려진다. 설계할 때 그것을
받아들이기로 하고 "번호에 빈 자리가 생길 수 있다" 고 적어 두었다.

실제로 연결을 30% 확률로 끊고 재 보니 빈 자리가 하나도 없었다.

| | MongoDB | PostgreSQL |
|---|---|---|
| 저장된 건수 | 4,425 | 1,200 |
| 빈 자리 | 0 | 0 |
| 중복 번호 | 0 | 0 |

이 실험을 하기 전까지 누적된 것을 전부 포함한 수치다. 끊긴 연결은 드라이버가 다시
붙어 처리했다.

**빈 자리를 견디게 만들어 두었지만 이 조건에서는 생기지 않았다.** 생기지 않는다는 것을
확인한 것이지 생길 수 없다는 뜻은 아니다. 드라이버가 다시 붙지 못할 만큼 오래 끊기면
달라진다.

## Redis 가 끊기면 아무것도 저장되지 않았다

번호를 못 받으면 저장을 막게 만들어 두었다. 번호 없이 저장하면 그 메시지만 순서를
정할 근거가 없어 화면에서 자리를 못 잡기 때문이다.

Redis 를 끊고 200건을 보냈다.

| | 값 |
|---|---|
| 새로 저장된 문서 | 0 |
| 번호가 없는 문서 | 0 |

막히기는 했다. 다만 **막힌 자리가 예상과 달랐다.** 번호 발급에서 걸린 것이 아니라
연결 단계에서 먼저 걸렸다. 접속 상태를 Redis 에 쓰는 곳이 있어 웹소켓을 붙이는 것부터
실패했다.

그래서 이 실험으로 확인한 것은 "Redis 가 없으면 채팅이 통째로 서고, 번호 없는 문서는
생기지 않는다" 까지다. 번호 발급만 실패하고 나머지는 멀쩡한 상황은 만들지 못했다.

## 아직 하지 않은 것

- **번호 발급만 골라 실패시키지 못했다.** Redis 를 끊으면 연결부터 막힌다. 발급 경로만
  실패시키려면 그 자리에 따로 손을 대야 한다.
- **오래 끊긴 경우를 재지 않았다.** 드라이버가 다시 붙는 짧은 끊김만 봤다.
- **결제 쪽에는 주입하지 않았다.** MySQL 앞에도 프록시를 둘 수 있지만 이번에는 채팅만 했다.
- **지연이 길어질 때 줄이 어디까지 늘어나는지 재지 않았다.** 300ms 하나만 봤다.
