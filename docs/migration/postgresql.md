# MySQL 과 MongoDB 를 PostgreSQL 로 옮겼다

판단 근거는 [저장소 선택](../decisions/datastore-choice.md)에 있다. 여기는 옮기면서 무엇이
드러났는지를 적는다.

## 옮기기 전에 잰 것

무엇을 다시 검증해야 하는지부터 셌다.

| | 값 |
|---|---|
| JPA 엔티티 | 32개 |
| 네이티브 쿼리 | **0개** |
| MongoDB 를 쓰는 파일 | 4개 |

네이티브 쿼리가 없다는 것이 컸다. MySQL 쪽은 드라이버와 방언 교체가 대부분이었다.

## 무엇이 사라졌나

### active_key 열

살아 있는 결제를 대여 건과 종류마다 하나로 묶는 제약을, MySQL 에서는 열을 하나 두고
취소할 때 비우는 방식으로 흉내 냈다. 유니크 인덱스가 빈 값을 서로 다른 것으로 본다는
성질에 기댄 것이다.

이제 조건부 인덱스로 건다.

```sql
CREATE UNIQUE INDEX uk_payment_active ON payment (rental_his_id, payment_type)
  WHERE status <> 'CANCELED';
```

열도, 취소할 때 비우는 코드도, 그 규칙을 설명하는 주석도 없어졌다.

### 문서 저장소의 조건부 인덱스도 같은 모양이 됐다

채팅 메시지의 전송 식별자 유니크도 같은 문제였다. `sparse` 를 썼다가 식별자 없는 두
건이 부딪혀 조건부 인덱스로 바꿨던 것인데, PostgreSQL 에서 문장이 거의 같다.

```sql
CREATE UNIQUE INDEX uk_chat_message_client_id ON chat_message (chat_room_id, client_message_id)
  WHERE client_message_id IS NOT NULL;
```

**저장소를 옮기며 두 곳의 우회가 같은 한 가지 기능으로 수렴했다.**

## 옮기면서 드러난 것

### 빈 값을 어디에 놓는지가 다르다

방에서 가장 큰 번호를 찾는 질의가 틀린 답을 냈다. 번호를 채우기 전 메시지가 맨 앞에
와서 가장 큰 번호를 0으로 읽었고, 이미 쓴 번호를 다시 내줬다.

**PostgreSQL 은 내림차순에서 빈 값을 먼저 놓는다.** 문서 저장소에서는 빈 값이 가장 작은
것으로 취급돼 내림차순에서 맨 뒤로 밀렸다. 같은 질의가 저장소에 따라 다른 답을 준다.

번호가 없는 것을 조건에서 빼서 해결했다. 백필 테스트가 `[1, 2, 7]` 을 내놓아 잡혔다.
이 테스트가 없었으면 운영에서 번호가 겹친 뒤에 알았을 것이다.

### 시각의 정밀도가 다르다

순서가 뒤집히는 것을 재현하는 테스트가 통과하지 못했다. 뒤집힘이 0이 나왔다.

**PostgreSQL 은 마이크로초까지 저장한다.** 문서 저장소는 밀리초까지였다. 값이 잘 겹치지
않으니 "같은 시각에 저장된 것들의 순서를 시각으로 정할 수 없다"는 성질이 드러나지 않는다.

정밀도가 올라간 것은 이득이지만 **순서를 시각으로 정할 수 없다는 사실은 그대로다.**
시계가 다른 서버가 둘이면 마이크로초도 겹친다. 테스트에서 밀리초로 잘라 원래 조건을
만들고, 왜 자르는지를 적어 두었다.

### 방언을 못박아 두면 저장소를 못 바꾼다

`spring.jpa.database-platform` 에 `MySQL8Dialect` 가 적혀 있었다. 드라이버와 접속 정보를
바꿔도 DDL 이 MySQL 문법으로 나가 테이블이 만들어지지 않았다.

지우면 Hibernate 가 연결에서 알아낸다. **못박아 둘 이유가 없었다.**

### 예외 이름이 다르다

같은 전송이 두 번 저장되는 것을 막는 자리에서, 문서 저장소는 `DuplicateKeyException` 을
관계형은 `DataIntegrityViolationException` 을 준다. 둘 다 스프링이 옮겨 준 것이라 이름만
다르다.

JPA 에서는 `save` 만 부르면 제약 위반이 트랜잭션이 끝날 때 터진다. 그때는 잡으려던 자리를
이미 지나쳤다. `saveAndFlush` 로 바꿔 그 자리에서 잡게 했다.

**이 메서드에 트랜잭션이 걸려 있지 않은 것이 여기서 중요하다.** 저장소 호출마다 트랜잭션이
따로 열리므로 실패한 flush 가 뒤의 조회를 망치지 않는다. 한 트랜잭션 안이었다면 영속성
컨텍스트가 망가져 다시 조회할 수 없다.

## 옮긴 뒤 다시 잰 것

단위 실험에서 수치가 같다.

| 잰 것 | MongoDB | PostgreSQL |
|---|---|---|
| 200건을 시각으로 정렬했을 때 뒤집힘 | 49 ~ 64 | 49 |
| 번호로 정렬했을 때 | 0 | 0 |
| 같은 식별자 16건 동시 저장 후 남은 것 | 1 | 1 |
| 번호 채우기 두 번 실행 | `[1,2,3,4,5]` 두 번 | 같음 |
| 이미 7번을 쓴 방에 채우기 | `[7,8,9]` | 같음 |
| 안읽음, 시각 대 번호 | 1 대 3 | 1 대 3 |

실부하도 같다.

| 잰 것 | MySQL·MongoDB | PostgreSQL |
|---|---|---|
| 웹소켓 200건 뒤집힘 | 0 | 0 |
| 유실 | 0 | 0 |
| 왕복 중앙값 | 1.24 ~ 1.45s | **0.70 ~ 1.19s** |
| 결제 16건 동시 요청 | 16 성공, 결제 1건 | 같음 |

왕복이 조금 빨라졌다. 저장소가 셋에서 둘로 줄어 한 건을 처리할 때 건너는 곳이 하나 줄었다.
다만 이 값만으로 PostgreSQL 이 더 빠르다고 말할 수는 없다. 같은 기계에서 컨테이너 수가
줄어든 것도 함께 작용한다.

## 아직 하지 않은 것

- **데이터를 옮기지 않았다.** 스키마를 새로 만들었다. 실제로 쓰던 데이터가 있으면
  MongoDB 문서를 읽어 넣는 일이 따로 필요하다.
- **채팅 메시지를 파티셔닝하지 않았다.** 한 테이블에 쌓인다. 월별로 자르는 것은
  건수가 늘어난 뒤에 판단한다.
- **운영 compose 를 옮기지 않았다.** 로컬만 바꿨다.
- **Elasticsearch 는 그대로다.** 색인 대상이 상품이라 이번 이행과 겹치지 않는다.
