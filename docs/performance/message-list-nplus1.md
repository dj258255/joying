# 답장이 섞이면 목록 조회가 여섯 배 느려졌다

## 어디에 적혀 있었나

코드에 주석으로 적혀 있었다.

```
/**
 * 답장 대상 메시지. 답장이 아니면 null.
 *
 * <p>목록을 만들 때 메시지마다 이 조회가 한 번씩 더 나간다.
 */
```

알고 있었지만 얼마나 느려지는지는 재지 않았다. 재지 않으면 고칠 값이 있는지 알 수 없다.

## 잰 조건

방 두 개를 만들어 다른 조건을 똑같이 두고 답장 비율만 갈랐다.

| 항목 | 값 |
|---|---|
| 도구 | k6, 가상 사용자 10명이 25초 동안 계속 조회 |
| 요청 | `GET /api/v1/chat-rooms/{방}/messages?size=50` |
| 방 9101 | 메시지 500건, 답장 0건 |
| 방 9102 | 메시지 500건, 답장 499건 |

실행: `ROOM=9102 k6 run load/k6/message-list-nplus1.js`

## 결과

저장소를 PostgreSQL 로 옮긴 뒤 같은 조건으로 다시 쟀다. 두 벌을 함께 적는다.

**PostgreSQL** (지금)

| | 답장 0건 (9101) | 답장 499건 (9102) |
|---|---|---|
| **고치기 전** p95 | 5.20ms | **99.61ms** |
| **고친 뒤** p95 | 7.20ms | **8.62ms** |

**MongoDB** (옮기기 전)

| | 답장 0건 | 답장 499건 |
|---|---|---|
| 고치기 전 p95 | 10.09ms | 59.55ms |
| 고친 뒤 p95 | 9.83ms | 10.12ms |

**PostgreSQL 에서 더 나쁘다.** 답장이 섞였다는 것만으로 MongoDB 는 여섯 배, PostgreSQL 은
열한 배 느렸다. 한 건씩 찾아오는 왕복 비용이 관계형에서 더 크다.

고친 뒤에는 양쪽 다 답장이 있으나 없으나 같다.

답장이 없는 방의 수치가 양쪽에서 같다는 것이 중요하다. 다른 것을 건드리지 않았다는
뜻이다.

## 어떻게 고쳤나

목록에 실을 답장 대상의 식별자를 모아 한 번에 가져온다.

같은 메시지에 여러 건이 답장할 수 있어 식별자를 모을 때 중복을 없앤다. 이 실험에서는
499건이 전부 같은 메시지를 가리켜서, 조회가 499번에서 1번으로 줄었다.

한 건을 내보내는 자리는 그대로 두었다. 메시지를 고치거나 지웠을 때 양쪽 화면에
반영하는 경로인데, 거기서는 애초에 한 건이라 모을 것이 없다.

## 지워진 메시지를 가리키는 답장

일괄 조회 결과에 없으면 `null` 이 되고 화면은 그것을 지워진 메시지로 표시한다.
한 건씩 조회할 때와 같은 동작이다.

메시지를 실제로 지우지 않고 표시만 하기 때문에 이 경우는 드물다. 다만 방을 지울 때는
메시지도 함께 지우므로, 지워진 방의 메시지를 가리키는 답장은 이 자리를 지난다.

## 답장이 서로 다른 것을 가리키면

앞의 실험은 499건이 **전부 같은 하나**를 가리켰다. 모아서 한 번에 가져오는 이득이 가장 큰
조건이다. 전부 다른 것을 가리키면 조회 횟수는 그대로 한 번이지만 **가져오는 양이 는다.**

방 셋을 같은 조건으로 두고 답장이 가리키는 곳만 갈랐다. 만드는 것은
`load/seed/seed-reply-rooms.sh` 다.

| 방 | 메시지 | 답장 | 가리키는 곳 |
|---|---|---|---|
| 9101 | 500 | 0 | 0 |
| 9102 | 500 | 499 | **1** (앞의 실험 조건) |
| 9103 | 500 | 499 | **499** |

예열한 뒤 셋을 번갈아 세 번 돌렸다. 번갈아 돌리는 이유는 기계가 시간에 따라 느려지거나
빨라지는 것을 한쪽에만 얹지 않기 위해서다.

**목록 조회 중앙값**

| | 1회차 | 2회차 | 3회차 |
|---|---|---|---|
| 9101 (답장 없음) | 4.86ms | 3.63ms | 3.06ms |
| 9102 (하나를 가리킴) | 4.44ms | 4.02ms | 3.84ms |
| 9103 (각자 다른 것) | **5.65ms** | **5.52ms** | **4.93ms** |

**세 번 모두 9103 이 가장 느리다.** 9102 와의 차이가 1.1~1.5ms 로, 25~40% 다.
9101 과 9102 사이에는 일정한 차이가 없다.

조회는 어느 쪽이나 한 번이다. 다른 것은 그 한 번이 가져오는 줄 수다. 9102 는 한 줄,
9103 은 화면에 실린 50건만큼을 가져온다. **예상한 자리에서 예상한 만큼 늘었다.**

고치기 전의 99.61ms 와 견주면 가장 나쁜 조건인 9103 도 5ms 언저리다. **모아서 가져오는
방식은 답장이 흩어져도 버틴다.**

조건: k6 가상 사용자 10명, 15초, 한 화면 50건. 이 기계에서 컨테이너로 띄운 것이라
**위쪽 표의 절대값과 견줄 수 없다.** 여기서 견줄 수 있는 것은 같은 자리에서 같은 조건으로
잰 세 방끼리다.

### 고치기 전과는 견주지 않았다

되돌려 다시 재지 않았다. 여기서 잰 것은 **고친 뒤 세 모양의 차이**다.

## 아직 하지 않은 것

- **한 화면에 50건을 기준으로만 쟀다.** 더 많이 읽을 때 어떻게 되는지는 재지 않았다.
- **검색과 앞뒤 조회도 같은 자리를 지나는데 따로 재지 않았다.** 같은 함수를 쓰므로
  같이 좋아졌을 것이지만 확인하지 않았다.
