# 섀도 리드가 0을 말한 뒤에 방 화면 읽기를 새 DB로 돌렸다

[무중단 이관](live-storage-split.md)의 남은 반이다. 이중 쓰기는 삽입만 비추므로
읽음 · 수정 · 삭제 같은 가변 열은 새 DB 에서 어긋난다. 어긋남을 보는 장치(섀도
리드)와 메우는 장치(가변 열 재동기화)를 만들고, 둘이 0 을 말한 뒤에 읽기를
돌렸다. 섀도 리드는 대규모 이관들이 쓴 검증 방식이다. 읽기 일부를 양쪽에 보내
결과를 비교한다. 가설과 판정 기준은
[#120](https://github.com/dj258255/joying/issues/120)에 먼저 적었다.

결론부터.

- **가변 열 드리프트는 실재하고 섀도 리드가 전부 잡았다.** 읽음 처리(49,997행) ·
  수정 3 · 삭제 3을 만들자 비교 10/10 이 불일치였다. 재동기화(50,000행 갱신) 뒤
  같은 비교 10건의 불일치 증가는 0, 불변 열 검증(행 수 · 꼬리 · 해시 표본)도 일치
- **읽기 전환 뒤 응답은 같고 속도는 기준 안이다.** 같은 조회 10개의 data 가
  10/10 일치(봉투의 응답 생성 시각만 다름). 목록 p95 는 워밍을 맞춘 회차에서
  옛 경로의 0.75~0.82배다
- **섀도 리드가 예고에 없던 결함 둘을 잡았다.** 드리프트를 넣기 전의 첫 비교가
  이미 불일치였는데, 원인이 [#100](https://github.com/dj258255/joying/issues/100)이
  예측한 번호 중복의 실물이었다(시드가 Redis 번호표를 안 맞춰 실송신 360건이
  시드와 같은 번호를 받음 → 동률 정렬이 비결정). 드리프트용 읽음 처리에서는
  읽음 표시가 서비스 이래 한 번도 적용된 적 없는 조용한 실패를
  발견했다([#121](https://github.com/dj258255/joying/issues/121), 비동기 스레드에
  트랜잭션이 없어 항상 예외 → runQuietly 가 삼킴)

## 구조

- 모드 셋(`joying.chat.read.mode`): old(기본) · shadow(옛 DB 응답 + 같은 조회를
  새 DB 와 비동기 비교) · new(새 DB 응답)
- 전환 범위는 방 화면 목록(첫 페이지 · before · after)뿐이다. 검색 · 단건 ·
  수정 · 삭제는 쓰기 컷오버 전까지 옛 DB 에 남는다(경계를 여기 적어 둔다)
- 비교 작업은 전용 1스레드 + 유한 큐(100)다. 공유 풀에 두면 몰린 조회가 풀
  경합을 다시 만든다(#116 의 실측). 넘치면 버리고 버린 수를 센다. 비교 실패는
  불일치가 아니라 모름이라 따로 센다(compared · mismatch · dropped · errors)
- 재동기화는 옛 DB 의 가변 열을 스테이지로 COPY 해 다른 행만 UPDATE 한다
  (`scripts/resync-chat-split-mutable.sh`, IS DISTINCT FROM 이라 NULL 차이도 잡음)

## 재는 자리를 또 틀렸다

- **검증 불일치의 첫 원인은 데이터가 아니라 타임존이었다.** 불변 열 체크섬이
  created_at 의 문자열을 쓰는데 새 DB 컨테이너가 UTC 라 모든 행의 표현이
  달랐다. 타임존을 맞추니 일치. 체크섬에 타임존 의존 표현을 넣으면 안 된다는
  기록
- **동등성 비교를 바이트로 하면 봉투가 걸린다.** 응답 봉투의 timestamp(응답
  생성 시각)는 당연히 다르다. data 만 비교해야 한다
- **시드가 번호표를 안 맞추면 #100 을 손수 재현하게 된다.** 시드는 DB 에 번호를
  직접 넣는데 Redis 번호표를 안 올려 두면 다음 실송신이 같은 번호를 받는다.
  동률 번호는 정렬을 비결정으로 만들고, 섀도 비교가 그것을 잡았다. 시드
  스크립트에 번호표 정렬을 넣었다

## 후속 수선: 지운 내용의 노출 창

이 측정의 드리프트는 "가변 열은 비추지 않는다"는 설계에서 왔는데, 그 창은 배지가
틀리는 것과 무게가 다른 경우를 하나 품고 있었다. 옛 DB 에서 지운 메시지가 새 DB
읽기에는 재동기화 전까지 살아 있다. 지운 내용의 노출이다. 그래서 삭제 · 수정 ·
읽음 묶음 갱신은 변경 시점에 새 DB 로도 비추게 바꿨다(mirrorMutable ·
mirrorReadFrom, 실패는 삽입 미러와 같은 규칙으로 세고 재동기화가 메움). 재동기화는
과거분과 미러 실패분을 메우는 장치로 남는다.

다만 미러가 실패한 창 동안은 새 DB 읽기가 지운 메시지를 여전히 내보낼 수 있다
(fail-open). 삭제를 막는 쪽(fail-closed)으로 바꾸려면 읽기가 옛 DB 를 다시 봐야
해서 전환의 의미가 없어지므로, 미러 실패 지표(chat.migration.mirror.failures)가
0 이 아닐 때 재동기화를 돌리는 운영 규칙을 경계로 둔다.

## 대가

- shadow 모드는 조회마다 새 DB 읽기 1회와 비교 1건을 만든다(전용 스레드 ·
  풀이라 응답 경로에는 안 얹힘, 큐가 차면 비교를 버리고 셈)
- new 모드에서도 답장 원본 조회와 검색은 옛 DB 를 본다. 읽기가 두 DB 에 걸쳐
  있는 기간이 존재하고, 그 경계는 이 문서와 코드 주석에 적어 둔다
- 재동기화는 전체 가변 열을 COPY 한다(144,380행 기준 수 초). 행이 수억이 되면
  updated_at 워터마크 같은 증분 방식이 필요하다

## 아직 하지 않은 것

- **쓰기 컷오버.** 정본은 여전히 옛 DB 다. 쓰기까지 돌리려면 배리어(#105) 아래서
  정본 교대와 역방향 이중 쓰기(되돌림용)를 설계해야 한다
- **섀도 비교의 표본률 제어.** 지금은 전수에서 큐가 차면 버리는 방식이다. 트래픽이
  크면 처음부터 N% 만 비교하는 쪽이 맞다
- **운영 알림.** mismatch 가 0 에서 1 이 되는 순간의 알림은 지표만 있고 경보는 없다
