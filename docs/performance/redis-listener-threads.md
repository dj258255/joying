# 메시지 한 건마다 스레드가 하나씩 생기고 있었다

## 어떻게 찾았나

전달 순서를 재다가 로그에 찍힌 스레드 이름을 보고 알았다. 찾으려던 것이 아니라
다른 것을 재다가 눈에 들어왔다.

```
redisMessageListenerContainer-1
redisMessageListenerContainer-3
redisMessageListenerContainer-5
...
```

번호가 계속 올라간다. 재사용되는 스레드가 아니다.

## 왜 그런가

`RedisMessageListenerContainer` 에 실행기를 지정하지 않으면 기본값이 쓰인다. 그 기본값은
**받은 메시지마다 새 스레드를 만들어 넘기는 방식**이다. Spring Data Redis 문서도 기본값
대신 스레드 풀을 지정할 것을 권한다.

이 프로젝트는 지정하지 않고 있었다.

## 잰 것

전달 경로에 스레드 이름을 찍고 같은 부하를 넣었다. 발신자 8명이 각 25건, 총 200건.

| | 전달 건수 | 그 일을 한 서로 다른 스레드 수 |
|---|---|---|
| **고치기 전** | 200 | 200 |
| **고친 뒤** | 600 (3회 합계) | 1 |

한 건당 하나씩 만들고 버리고 있었다. 고친 뒤에는 방 하나짜리 실험이라 줄이 하나만
쓰였다. 방이 여럿이면 방마다 다른 줄로 나뉜다.

순서는 양쪽 모두 뒤집힘 0이다. 왕복 중앙값 1.22 ~ 1.83초로 고치기 전과 비슷하다.
이 변경은 순서나 지연을 바꾸려는 것이 아니라 몰릴 때 스레드가 무한정 늘어나는 것을
막으려는 것이다.

## 어떻게 고쳤나

두 단계로 나눴다.

**받는 자리는 스레드 하나로 묶었다.** 여기서는 넘겨주기만 한다. 하나로 묶어야 Redis 가
보낸 순서가 그대로 유지된다. 풀로 두면 다시 뒤섞인다.

**실제 전달은 방 단위 실행기가 한다.** 받는 자리에서 오래 붙잡고 있으면 뒤에 온 메시지가
밀린다. 방 안에서는 순서대로, 방끼리는 동시에 나간다.

전달용 실행기를 메시지 처리용과 따로 둔 이유는 한쪽이 다른 쪽을 막지 않게 하기
위해서다. 같은 줄에 두면 저장이 늦어질 때 이미 저장된 것의 전달까지 함께 밀린다.

## 걸렸던 것

실행기가 둘이 되자 기동에 실패했다. `@Qualifier` 를 필드에 붙였는데 Lombok 이 만든
생성자에 따라가지 않아 어느 빈인지 고르지 못했다.

`@RequiredArgsConstructor` 는 필드 애너테이션을 생성자 파라미터로 자동으로 옮기지 않는다.
필드에 붙은 것이 파라미터에도 뜻이 통한다는 보장이 없어서다. 옮길 것을 `lombok.config` 에
적어야 한다.

```
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier
```

생성자를 직접 쓰는 방법도 있지만, 프로젝트 전체에 같은 상황이 또 생길 것이라 설정으로
해결했다.

## 재는 자리를 또 틀렸다

고친 직후 세 번 재서 전부 뒤집힘 0을 얻었다. 그런데 앱이 뜨지 않은 상태였다. 위의
`@Qualifier` 문제로 기동에 실패했는데, k6 는 연결 실패를 조용히 넘기고 0을 돌려줬다.

이 실험에서 세 번째다. 이제는 재기 전에 8080 포트에 무엇이 떠 있는지 먼저 확인한다.

## 아직 하지 않은 것

- **방을 여럿 두고 재지 않았다.** 방 하나로만 재서 줄 하나만 쓰였다. 방이 많을 때
  줄이 고르게 나뉘는지는 확인하지 않았다.
- **몰릴 때 큐가 얼마나 차는지 재지 않았다.** 받는 자리를 스레드 하나로 묶었으므로
  그 앞에 줄이 생긴다. 그 줄의 길이는 재지 않았다.
- **다른 리스너는 그대로다.** 타이핑과 읽음을 나르는 리스너도 같은 컨테이너를 쓰므로
  같은 실행기를 지나지만, 그쪽 부하는 재지 않았다.
