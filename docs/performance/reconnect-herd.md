# 쉰 명이 한꺼번에 다시 붙어도 전달은 밀리지 않았다

노드 사망이나 배포로 수십 명이 동시에 재접속하면, 재연결 핸드셰이크와 복구
조회(놓친 메시지를 after=번호로 당기는 HTTP)가 한꺼번에 몰린다. 그 폭주가 그
시간에 계속 붙어 있던 사람들의 전달을 미는지 쟀다. 가설(H4)과 판정은 재기 전에
[#95](https://github.com/dj258255/joying/issues/95)에 적었다. Slack 이 재접속
폭주를 받아 내려고 엣지 캐시(Flannel)를 따로 둔 것이 이 질문의 배경이다.

결론부터.

- **H4 기각.** 폭주 구간의 전달 p95(23~27ms)가 평시(24~27ms)와 같다. 2배는커녕
  차이가 없다
- 복구 조회 자체도 가볍다. 50건 동시 조회의 p95 가 8.8~13.8ms 다
- 사전 판정대로 **현 구조로 충분**하다고 기록하고 닫는다. 지터나 스냅샷 캐시
  같은 완화 장치는 이 규모에서 만들 이유가 없다

## 잰 조건

| 항목 | 값 |
|---|---|
| 서버 | 두 프로세스(8080 · 8081), 현행(node) 모드 |
| 도구 | k6, `load/k6/reconnect-herd.js` |
| 관찰 쌍 | 10쌍이 계속 붙어 200ms 간격으로 주고받으며 전달 왕복을 기록 |
| 폭주자 | 50명이 각자 방에 복구 재료 50건을 쌓은 뒤, 같은 시각에 일제히 끊고 재접속 + 복구 조회(after=절반 지점, 각 15건 회수) |
| 구간 | 평시는 폭주 직전 10초, 폭주는 재접속 뒤 10초. 구간은 태그로 나눠 같은 실행에서 비교 |
| 실행 | 3회. 시작 load 4.7~5.5 |

실행: `OBSERVER_PAIRS=10 HERD_SIZE=50 k6 run load/k6/reconnect-herd.js`
(방과 사람은 `load/seed/seed-order-rooms.sh 60` 으로 만든다)

## 결과

| 반복 | 평시 p95 | 폭주 p95 | 복구 조회 p95 | 재접속 수 |
|---|---|---|---|---|
| 1 | 25ms | 25ms | 12.1ms | 50 |
| 2 | 24ms | 23ms | 8.8ms | 50 |
| 3 | 27ms | 27ms | 13.8ms | 50 |

중앙값은 전 구간 14ms 수준으로 같았다. 폭주가 실제로 일어났다는 증거(재접속 50,
회수 750건)를 같은 실행에 남겼다. 0 과 "폭주가 없었음"을 구분하기 위해서다.

## 왜 안 밀리나

복구 조회는 `(chat_room_id, sequence)` 인덱스를 타는 좁은 범위 조회이고, 방마다
다른 방이라 한 줄(방 단위 실행기)에 몰리지 않는다. 재연결 핸드셰이크 50건도
인바운드 채널의 세션 단위 직렬화에 흡수된다. 이 규모에서는 폭주라고 부를 양이
아니었다.

## 재는 자리를 한 번 틀렸다

첫 측정은 평시 p95 가 1.1~1.5초로 나왔다. 폭주보다 평시가 나쁜 역전이라 의심해
보니, 폭주자 50명이 측정 시작 직후 복구 재료 2,500건을 한꺼번에 쌓는 단계가
평시 구간에 섞여 있었다. 기준선 오염이다. 구간을 셋(쌓기 · 평시 · 폭주)으로
나누고 평시를 폭주 직전 10초로 좁혀 다시 쟀다. 위 표가 그 결과다.

덤으로 하나 배웠다. **이 지형에서 전달을 미는 것은 재접속이 아니라 동시
송신**이다. 50명이 각 50건을 몰아 보내는 쌓기 단계가 관찰 쌍의 전달 p95 를
1.5초까지 밀었다. 송신 폭주는 이 측정의 목적이 아니라 수치로 확정하지 않지만,
다음에 잴 것이 생겼다.

## 아직 하지 않은 것

- **노드 사망과 함께 오는 폭주.** 여기서는 클라이언트만 끊었다. 노드가 죽으면
  재접속이 남은 노드 하나로 쏠리고 방 이동(consistent hash)도 함께 일어난다
- **규모.** 50명 기준이다. 수백 단위는 재지 않았다
- **동시 송신 폭주.** 위에서 드러난 1.5초는 조건을 고정해 따로 재야 한다
